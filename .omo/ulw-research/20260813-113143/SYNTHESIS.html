BurnGuard Design 경쟁 설계 조사

Executive summary

Claude Design을 따라가기 전에 로컬 권한 경계를 완성해야 한다

P0 ship blocker: Backend는 예측 가능한 127.0.0.1:14070에 bind하고 모든 route를 인증·Host·Origin·CSRF 검증 없이 mount한다. 프로젝트 삭제, 파일 patch, CLI turn, installer 같은 권한 있는 API가 포함된다. 기능 확대 전에 hostile-origin/Host 테스트와 per-launch capability가 필요하다. index.ts, server.ts, OWASP CSRF guidance.

BurnGuard에는 이미 채팅+iframe 캔버스, 요소 선택, 인라인 편집, CSS tweaks, 댓글, 드로잉, 프레젠테이션, 디자인 시스템 추출, 턴별 rollback, PDF/PPTX/HTML/handoff export가 구현되어 있다. 다음 차별화는 기능 수가 아니라 안전한 권한 경계, 실제 CLI 호환성, 대화 연속성, 턴별 변경 가시성, 구조화된 편집·export, 디자인 시스템 검증에서 나온다. README, ProjectView, checkpoints.

정확한 local-first

workspace와 system of record는 로컬에 남는다. 모델 문맥은 사용자가 선택한 CLI/provider 정책에 따라 처리된다. Zero-egress 또는 offline-only라고 주장하지 않는다. 현재 문구 · CLI 실행 근거

가져올 핵심 루프

대화로 생성 → 댓글·직접 편집으로 정밀화 → diff·rollback으로 안전한 탐색 → 디자인 시스템 검증 → 손실을 명시한 export/handoff. Claude 공식 가이드

명시적 비목표

실시간 협업, 조직 RBAC, infinite canvas, 범용 React codegen, plugin marketplace, 수십 개 API provider, cloud hosting은 현재 제품 경계 밖이다. BurnGuard 경계

Canonical product

Claude Design에서 가져올 것은 UI 외형이 아니라 작업 분업이다

Claude Design은 generic Artifacts의 별칭이 아니라 Anthropic Labs에서 시작한 별도 beta 제품이다. 현재 공식 자료는 chat-left/canvas-right workflow, design-system inheritance, comments/direct manipulation, design directions, organization collaboration, PDF/PPTX/HTML export, Claude Code·MCP handoff를 구분해 설명한다. 2026-04-17 출시 발표문, 제품 페이지, 시작 가이드.

현재성 경계: 출시 발표문의 “research preview”와 Opus 4.7 표기는 역사적 기록이다. 2026-08-13 현재 제품은 beta이고 Chat·Cowork·Claude Code와 사용량을 공유한다. 현재 공식 문서는 아홉 connector, MCP, /design-sync, /design, drag/resize/align, Enterprise 디자인 시스템 관리 권한을 추가로 설명한다. 인증된 실제 제품과 MCP 도구 계약은 이 조사에서 실행하지 않았다.

그대로 강화

  • Chat: 구조·전체 방향 변경
  • Comments: 특정 component 수정
  • Direct edit: 빠른 text/style 수정
  • Design-system Draft→Review→Publish
  • HTML/PDF/PPTX/handoff

BurnGuard식 재설계

  • Named direction 전에 per-turn diff
  • 범용 drag 전에 deck-only eligible element 실험
  • Auto-correction 전에 explainable validation report
  • Cloud share 대신 versioned portable bundle
  • Remote MCP 전에 localhost authority와 workspace trust
공식 가이드의 가장 재사용 가능한 패턴은 brand constraint를 한 번 encode하고, macro edit·localized comment·direct manipulation을 분리하며, 다른 방향을 시도하기 전에 현재 상태를 보존하는 것이다. Design-system 가이드, 관리자 가이드.

검증할 BurnGuard 설계 가설: visual targeting(identity → typed bridge → transaction)과 change control(mutation lock → diff → restore)을 먼저 분리한다. 하나의 universal 경쟁 패턴이나 해자로 주장하지 않는다. Duplicate node ID는 first-match 오편집을 만들 수 있으므로 자동 복구가 아니라 fail-closed integrity validator부터 검증한다. Git은 checkpoint 교체 결정이 아니라 bounded snapshot·delta와 비교할 benchmark 후보다.

GitHub stars와 README fidelity 수치는 발견 신호일 뿐 구현 증거로 사용하지 않았다. Presenton exporter 공개 범위는 미검증이며, AGPL·source-available·unknown license와 vendored lineage는 path별 provenance·NOTICE·SBOM gate 전에는 donor가 아니다.

Defensibility

경쟁군 비교에서 도출한 차별화 축

BurnGuard의 해자는 “AI가 디자인한다”거나 “로컬에서 돈다”는 단일 기능이 아니다. 그 문구는 경쟁사가 복제하기 쉽다. 방어 가능한 조합은 다음 네 자산이 함께 축적될 때 생긴다.

1. 사용자 소유 프로젝트의 장기 기록

설치형 CLI가 실제 workspace를 수정하고, 매 턴 diff·검토·복구·출처가 남는다. 다른 서비스로 옮길 수 있으면서도 과거 의사결정과 검증 이력 때문에 계속 사용할 이유가 생긴다.

2. 디자인 시스템 증거 corpus

토큰 추출 결과만 저장하지 않고 source provenance, 누락, 대체, 승인·publish 상태와 artifact 검증 결과를 fixture로 축적한다. 고객별 corpus가 커질수록 결과 예측성과 조직 신뢰가 높아진다.

3. loss-aware handoff

HTML을 canonical source로 유지하면서 PDF·PPTX·handoff마다 지원 요소와 손실을 manifest로 공개한다. “완벽한 export” 마케팅보다 재현 가능한 호환성 matrix가 구매 위험을 낮춘다.

4. CLI-agnostic local control plane

모델·provider를 다시 만드는 대신 사용자가 이미 인증한 CLI의 capability를 정확히 탐지하고, workspace trust·mutation lock·diagnostics·redaction을 공통 정책으로 제공한다.

초기 판매 가설: 민감한 브랜드 자산과 실제 codebase를 외부 SaaS editor에 올리기 어렵고, 결과물의 검토 가능성과 PPTX·PDF handoff가 필요한 제품·브랜드 팀이다. 운영 증거의 축적이 차별화 후보이며 지불 의사와 전환 비용은 고객 인터뷰와 유료 pilot으로 검증해야 한다.

반대로 provider 수, marketplace 규모, generic template 수, “완전 local” 문구 자체는 해자가 아니다. 상세 근거는 Markdown 원본 §4.4에 있다.

Guardrails

계획에 박아야 할 위험과 방어선

Authority

Per-launch capability, non-simple header, strict Host/Origin, stale token rejection. CORS만으로 보호했다고 간주하지 않는다. OWASP

Filesystem

realpath containment, symlink/reparse rejection, zip traversal test, path normalization을 read/write/copy/export 전체에 공통 적용한다.

CLI drift

Version detection이 아니라 exact harmless invocation과 output parser fixture로 capability를 판정한다. Backend parity를 가정하지 않는다.

Export honesty

“Editable PPTX parity”를 약속하지 않는다. 요소별 support table과 explicit loss report, PowerPoint/LibreOffice QA가 완료 조건이다.

License provenance

Pinned SHA, file lineage, nested license, NOTICE, attribution을 검토한다. AGPL·unknown·source-less converter는 code donor가 아니다.

Data recovery

Checkpoint는 rollback이지 backup이 아니다. Portable bundle에는 schema version, secret exclusion, clean-profile restore test가 필요하다.
